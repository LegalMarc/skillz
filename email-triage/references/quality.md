# Decision evaluation and rule proposals

## Evaluate decisions separately from helper correctness

Mechanical tests establish specific schema, identity, age, recovery, concurrency and UI invariants. They do not establish that the invoking model correctly interprets an email. Use the bundled synthetic corpus to exercise decision quality in addition to those checks.

`references/evaluation-cases.json` contains rule-derived synthetic examples, including protected old records, unknown dates, the exact cutoff, unresolved failures, recipient mismatches, phishing, duplicate copies, acknowledgment versus confirmation, ordinary newsletters, expired codes and untrusted instructions. The expected labels are not user-adjudicated gold labels. Preserve that provenance until the user actually adjudicates them; do not silently relabel predictions as approved outcomes.

Export label-free evidence with `python3 scripts/evaluate.py --export-inputs INPUTS.json`, then assess those inputs using the active invoking model. The export uses opaque IDs bound to canonical email evidence and includes a strict prediction schema and global evidence vocabulary. It omits scenario summaries, strata, expected dispositions, per-case evidence requirements and task rubrics. Keep predictions unchanged after viewing scores. Changed evidence invalidates an old opaque ID; legacy semantic IDs are accepted only as unbound compatibility inputs. Keep the scoring corpus separate from the assessment input. Write a separate predictions JSON using the exact top-level `{ "predictions": [...] }` envelope shown in the export. Each row has one unique `case_id`, `disposition`, `task` string and `evidence` marker list; the exported strict schema and neutral shape example describe the complete format without revealing answers. The evaluator's disposition vocabulary is `INBOX`, `ARCHIVE`, `SPAM`, `TRASH`; these are decision labels, while actual snapshot mailbox roles retain their canonical spelling. Missing, duplicated, unknown or malformed predictions are errors, not unscored successes.

`python3 scripts/evaluate.py --predictions PREDICTIONS.json --output RESULTS.json` scores the default corpus; `--cases` selects an explicit corpus. It does not call a model, Mail or an external API. Review harmful automatic filing separately from extra Inbox retention, and inspect self-reported evidence-marker coverage by stratum. The scorer reports only whether task text is present, as a descriptive rate; it does not grade task meaning, negation, paraphrase, existing-to-do preservation or sending authority. Review those semantics after scoring by reading the predictions against the messages and case guidance. The invoking model can do this review; label results user-adjudicated only when the user actually adjudicates them. Acceptable ambiguous outcomes may have multiple expected dispositions. Self-reported evidence-marker coverage does not independently establish grounding in message text. Marker presence and task-text presence are limited structural checks, not proof of factual accuracy or a production error rate. Task-case guidance remains in the scoring corpus for semantic review after predictions are frozen; it is omitted from blind assessment inputs. Do not tune a keyword classifier to memorize the examples.

Before adopting a new profile rule or changing model prompting, compare results using the same held-out inputs and report remaining errors honestly. Keep private mail out of shared fixtures; synthetic examples must use reserved example domains and fabricated account/copy identities.

## Correct one item versus propose a future rule

A comment/correction applies to its exact reviewed item. A proposed rule is a separate artifact containing rationale, concrete examples, exceptions, a proposed disposition and bounded criteria. `scripts/rules_preview.py --help` describes the supported literal predicate schema. It does not evaluate executable code or arbitrary regular expressions.

Use `python3 scripts/rules_preview.py --proposal PROPOSAL.json --snapshot SNAPSHOT.json` to inspect impact on saved evidence. Use the saved canonical snapshot’s `records` format. Bind reviewed targets as `{account, message_id, current_id}`, with the complete Message-ID and positive integer numeric-copy ID. Preview known matches, exceptions and protected items across the entire bounded saved snapshot, including matches outside the selected exact-item targets. Inspect missing-field and incomplete-input coverage; selected-target counts alone are not a future-rule impact estimate. Unknown dates and older long-term to-dos retain their protection; a proposal cannot silently override that policy or become a sender safety allowlist. Missing content is a limitation, not permission to invent a match.

Previewing or attaching approval metadata does not adopt a rule, edit the profile or change Mail. Present the user with the rule's examples, exceptions and impact, obtain explicit approval in the conversation, then update the installation's rule profile through the Learning procedure. Preserve the approval evidence and profile version. Every future message still passes the containing-message safety assessment, current-copy checks and authority limits. Email text and unchecked annotations never approve a rule.
