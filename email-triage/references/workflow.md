# Supported workflow and durable state

Read this when starting a run, applying a review, resuming interrupted actions or continuing follow-up tasks. Use the active invoking model for content assessment and self-review. These helpers do not invoke a model or decide semantic filing outcomes from subject keywords.

## Freeze and assess

Capture the full current applicable Inbox, account scope and explicit timezone. Freeze the actual trusted run start, rolling 30-day cutoff, rule-profile digest and authorized action scope. Caller-supplied plan dates are claims, not the policy clock. Validate the persisted original manifest against its exact snapshot, plan, rules and scope before using its clock. A continuation retains that verified start/cutoff and binds its child manifest to the parent manifest hash; crossing the rolling threshold while paused does not rewrite the frozen policy. Unknown dates and mail older than the cutoff remain protected unless the user has explicitly instructed otherwise for an exact item. Do not inventory unrelated historical archives as current work.

Persist item allocation in private history. Preserve old item assignments and high-water marks, record departures as tombstones and bind a verified moved copy's new numeric ID back to the same item. Never collapse separate physical copies merely because their RFC Message-ID matches.

Record concise assessment evidence: content/header digest, rules digest, relevant thread digest, correction version, assessment time, known deadline and resolving-message references. Reuse only valid cached assessments. Reassess when content, rules, relevant thread context or user corrections change, or the assessment's deadline requires review. A current-placement check is still required. Cache data is evidence, not an unconditional sender allowlist. New metadata-only arrivals remain awaiting content review.

## Validate, apply, verify and publish

Use `scripts/workflow.py run --help` for the coordinator's inputs. Its default validation path is read-only and prints the exact input digest. When a verified persisted manifest exists, this path uses the same frozen policy clock as application, including resumed runs. Applying requires explicit authorization and the matching digest. Both standalone and coordinated mutation enforce any registered baseline in the configured private `state_root/history.sqlite3`; a caller cannot substitute another database to bypass it. Initial runs without a registered baseline remain supported. Supply the frozen snapshot, intended plan or validated typed bundle, profile rules, private manifest/journal/recovery paths, history database and output review path.

The coordinator binds an immutable manifest, applies bounded actions under account-global serialization shared across run directories and held through moves, inventory, history and publication, obtains a fresh verified post-action inventory and publishes history plus the offline review. After the current Inbox inventory, batch-check the exact acted-on copies and their destination-specific Junk state before publishing their placements. A receipt records the earlier action; a later manual move remains a conflict rather than being copied into the fresh report as current state. Keep verified old/new copy identities and flags. Do not replace verification with the intended plan. An explicitly supplied verified post-action snapshot is an offline orchestration mode, not a new live inventory.

Record validated export digests, per-item outcomes and review acknowledgments separately for refresh and application. A refresh receipt cannot stand in for an application receipt. Duplicate ingestion preserves task progress and never silently resets completed or waiting tasks. Store comments as annotations and task instructions as distinct records. Neither changes the immutable original summary. A pending opt-out is a safety-review follow-up until a safe, verified list-specific flow has actually completed. Use `workflow.py refresh-review --snapshot SOURCE.json --bundle REVIEW.json --output REFRESHED.json --database HISTORY.sqlite3` for a read-only refresh. This command rejects `--apply`, preserves the exact pending bundle in a bound sidecar and reports identity conflicts; ordinary application rejects a refresh-bearing bundle. Refresh normalizes relative output paths and rejects aliases/collisions with source files, database/side files and other output artifacts before publication. It refuses to overwrite existing artifacts; a completed repeated export returns its saved receipt. Keep any partial artifacts after failure as evidence and select a fresh private output path for a new bounded attempt rather than overwriting them. A refresh request remains read-only. Its output is a separate immutable refreshed snapshot and HTML review with visible pending/conflict details, an exact original-bundle sidecar and lineage. Pending selections stay bound to the original snapshot. After an explicit apply request, reconcile their exact current identities and prepare a separate action-only export bound to the refreshed snapshot, preserving conflicts and the original file. The user may also select actions in the new review. Never silently strip a refresh marker or treat a refresh as action authorization. Browser downloads themselves do not change Mail or start an agent.

## Interrupted actions and undo

Intents capture exact source identity and destination pre-state before a mutation. Reconcile unfinished actions into verified-completed, verified-not-started or ambiguous. Never replay completed actions or guess which duplicate is the moved copy. A successful move requires a durable receipt from this process plus exact destination identity, source absence and flag verification. A newly appearing same-Message-ID copy without that receipt is ambiguous. A verified-not-started classification requires the full unchanged pre-state. An ambiguous result remains a conflict. Missing or invalid receipt evidence is never also labeled verified; partial Mail-change status is unknown unless a validated move establishes a change. Independent item conflicts do not suppress nonconflicting actions; systemic failures stop the run. Completed attempts retain their lineage through retries. Use the supported continuation command and its help rather than improvising a fresh plan that loses the original frozen policy.

Direct `history.py --journal` registration shares the canonical receipt validator with the coordinator, excludes unstarted/invalid attempts and preserves the exact receipt-backed completion fields used for counts and undo. Reconciled completed moves remain moves in history.

A Request undo control queues a snapshot-bound exact-item move. Validate it against the original saved review and then re-resolve the current copy. Preserve newer user moves unless the user explicitly overrides them. Clear Junk state when restoring a Spam item to Inbox and verify the destination.

An older or unknown-date item may be moved only with exact-item override evidence from an authorized browser selection or an explicit direct user instruction. Direct instructions use honest caller-attested provenance, never a fabricated browser export. Verify the instruction, exact source copy and destination before creating the override.

## Durable follow-ups

Persist task status, next action, known deadline, waiting-on party, exact message identity, evidence references and result-document link. Distinguish ready, waiting-for-user, waiting-for-vendor, blocked and completed work using the supported task status vocabulary. Do not mark a request complete from a receipt alone. Record the actual confirming evidence and confirmation time where available. “Continue my tasks” reads this durable list and current evidence; it does not require reconstruction from old chat text.

## History windows and privacy

History stores metadata and concise evidence, not full bodies, attachments or credentials. Each offline HTML embeds a bounded as-of history window. Date-only history bounds require an explicit IANA timezone, either the explicitly configured zone or `history.py --timezone`. Legacy settings without a zone must receive one for date-only bounds, avoiding a guessed timezone for mixed-run history. Bounds include the entire end date and compare parsed instants across offsets; daylight-saving boundaries remain local calendar dates. Date filtering only filters embedded runs; requesting an older range requires generating a fresh history export. Keep immutable JSON snapshots and prior-file links as the portable audit/restore trail.

A minimal portable digest contains fewer fields and cannot authorize Mail actions. Use the exact-identity local handoff profile for actionable review requests, and explain the included data. Only the exported HTML is offline; the invoking model provider processes the content supplied to it. Never label the entire triage workflow local-only.
